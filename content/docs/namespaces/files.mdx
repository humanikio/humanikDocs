title: Files

A **bucket** is a named container for files inside a namespace. A **file** is one
document in a bucket: its contents, and enough description for an employee to
find it later without being told where it is.

Buckets are the file side of a namespace, next to the tables. Both live in the
same namespace and both are covered by the same grant. See
[Namespaces](/docs/namespaces).

## Every file has a path

A path is the address of a file inside its bucket.

```
/contracts/2026/acme-msa.pdf
/contracts/2026/globex-renewal.pdf
/handbook/expenses.md
```

Two rules govern it:

- **A path is unique within its bucket.** Two files in one bucket cannot share
  a path. The same path in a different bucket is a different file.
- **Case matters.** `/Contracts/acme.pdf` and `/contracts/acme.pdf` are two
  different addresses.

The path is how an employee acts on a specific file. It searches to find out
which document it wants, then uses the path it was given to fetch that one.

## Folders

Folders are part of the path rather than separate things you have to set up. A
file at `/contracts/2026/acme-msa.pdf` is in a folder called `2026`, inside one
called `contracts`, and both of those appear as soon as the file does.

You can also create an empty folder before there is anything in it, which is
useful when you are laying out a structure you intend to fill. An empty folder
stays until you delete it.

### Moving and renaming is immediate

Moving a file to another folder, or renaming a folder with a thousand files in
it, takes the same time as renaming an empty one. Nothing is copied and nothing
is re-uploaded.

This is worth knowing because it is often the opposite of what people expect from
file storage. You can reorganise a large bucket freely, at any time, without
waiting and without paying for the reorganisation.

<Callout type="warn">
  **Deleting a folder deletes everything inside it.** Every file below that
  folder is removed, at every depth. Nothing is moved up a level and nothing is
  kept.
</Callout>

## Adding a file

Files are uploaded through the platform. There is no direct upload to storage and
no separate storage account to configure.

| | |
| --- | --- |
| Maximum size | 50 MB per file |
| Type checking | None. The type is recorded as sent |
| Uploading to a taken path | Refused. To change a file, replace or edit it (below) |

Uploading returns as soon as the file is stored. Preparing it for search happens
afterwards, which is why a file can be listed and downloaded before it becomes
searchable.

## Changing a file

A file's contents can be replaced or, for text, edited in place. Either way the
file keeps its id and path, and the previous contents are kept as a **version**.

Every file has a `version` number that goes up by one with each change. A change
must say which version it was based on (`ifVersion`). If someone else changed the
file in the meantime, the change is refused with `409` and the current version, so
two people or two employees never silently overwrite each other. Look at the file
again and redo the change on what it says now.

### Text files

Markdown, plain text, CSV, JSON, YAML, HTML and other text files up to 2 MB can be
written and edited by sending the text itself. No file upload and no encoding.

- **Write** saves text at a path. If a file is already there it is replaced only
  when you send its current version.
- **View** returns the file as numbered lines with its version.
- **Edit** changes part of the file: replace an exact piece of text, which must
  appear exactly once, or insert lines after a line number. All the edits in one
  call are saved together, or none are.

Edits keep the file's own line endings. The text is current as soon as the edit
returns; the description used by search is rebuilt shortly after the last change.

This is also how Nova saves and edits documents in a bucket.

[How a file is edited](/docs/namespaces/editing-files) walks through every step between
sending an edit and the new version being saved, with a diagram.

### Versions

The 20 most recent earlier versions of each file are kept. You can list them and
restore one. A restore saves the old contents as a new version, so it can be
undone the same way.

```bash
curl -X POST "$HOS_API/namespaces/ns_orders/buckets/7c0e2b5a-31d4-4f7e-9a1c-2b8d6e4f9a10/objects/3f1d9c2e-8a47-4b6e-9d15-6c2a0e7b4f81/edits" \
  -H "Authorization: Bearer $HOS_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "ifVersion": 4,
    "edits": [
      { "type": "replace", "oldText": "Step 1: say hello", "newText": "Step 1: greet them by name" }
    ]
  }'
```

## Downloading a file

Reading a file gives you a **download link that works for one hour**.

<Callout type="warn">
  **The link is the permission.** Anyone holding that link can download the file
  until it expires, whether or not they have access to the namespace. It is not
  cancelled by deleting the file or the bucket. Treat it the way you would treat
  the file itself, and do not paste it anywhere you would not paste the document.
</Callout>

## Finding a document by meaning

An employee can search a bucket by describing what it wants rather than naming
the file. Asking for "the Acme renewal from last year" returns the document even
when nobody remembers what it was called.

This works because each file is described when it is uploaded, and the search
matches against that description.

### It has to be turned on for the namespace

Search by meaning is a setting on the namespace. It is on by default.

Two consequences that surprise people:

- **A file can be ready and still not searchable.** Ready means the file is
  stored and can be listed and downloaded. Whether it can be found by meaning is
  a separate question.
- **Turning the setting on is not retroactive.** Files uploaded while it was off
  are not processed later. To make an older file searchable, upload it again.

<Callout type="warn">
  **Preparing files for search uses platform credit.** This happens on upload,
  once per file. It is not covered by your own model key if you have supplied
  one, and it is not counted against a budget. If you are loading a large number
  of files and do not need to search them by meaning, turn the setting off for
  that namespace first.
</Callout>

## Deleting

Deleting a file removes it, its contents and all of its earlier versions.
Deleting a bucket removes every file in it. Deleting the namespace removes every bucket in it, and their files.

None of these are reversible, and nothing is archived first.

## What buckets do not do

- **No per-bucket or per-file permissions.** The namespace is the unit of
  access, so anyone who can read the namespace can read every bucket in it.
- **No long history.** Only the 20 most recent earlier versions of a file are
  kept, and none survive deleting the file.
- **No storage limit.** Nothing caps the number of buckets or files, or the total
  size.
- **No reprocessing.** A file that failed to prepare for search is not retried.
  Upload it again.
