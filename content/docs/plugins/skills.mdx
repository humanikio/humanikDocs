---
title: Plugin skills
description: The document generated from a plugin, and what makes it worth trusting.
---

Connecting software gives an employee two separate things.

The **plugin** is the connection: a host, an authentication scheme, and a
reference to a credential. It is what the office uses to actually make a call.

The **skill** is a Markdown document describing that software, generated from the
plugin record. It is what the employee reads to know the connection exists
and what to do with it.

<Callout>
  **This page is about skills that come from a plugin.** For what a skill
  is in general, how it reaches the employee, and how it differs from a protocol,
  see [Skills and protocols](/docs/skills-and-protocols).
</Callout>

## How the document gets written

Two steps, both automatic.

<Steps>

<Step>
**Sync.** The plugin is linked to a skill document. The link is a stable
back reference, so the same plugin always updates the same skill rather than
creating a second one.
</Step>

<Step>
**Compile.** A model reads the plugin record and writes the body: what the
software is, what each declared endpoint does, and what arguments it takes. It is
also shown the version it is replacing, so a rewrite builds on what is already
there instead of starting from nothing.
</Step>

</Steps>

The record is the input. Everything the document says about your software is
derived from what the plugin declares, which is why
[declaring endpoints](/docs/plugins/creating#endpoints-are-the-part-that-matters)
is the highest value thing you can do to a connection.

## What a regeneration keeps

A rewrite is shown the previous body, and what it may do with that body depends on
what the body was worth.

| Previous `contentSource` | What the rewrite does with it |
| --- | --- |
| `manual` | Preserves it. Wording, examples and ordering stay, and only what the plugin contradicts is changed |
| `verified` | Reproduces every endpoint, parameter and response shape exactly. Prose and ordering may improve, paths may not change |
| `generated` | Reuses the structure, and re-derives the claims from the plugin record |

The `generated` rule is the strictest on purpose. An endpoint in an unconfirmed
document was written by a previous run of the same process, so treating it as
evidence would let one guess become permanent by repetition.

<Callout type="warn">
  **A rewrite that would know less than the document it replaces is refused.**
  When a plugin declares no endpoints, there is little for a rewrite to
  re-derive claims from, and the result can be a thinner document than the one it
  replaces. That is not an improvement: skills have no version history, so a
  section lost this way cannot be recovered. A rewrite that drops whole sections
  is retried with the missing headings named, and if it still comes back short,
  the existing skill is kept and the compile reports why. The usual cause is a
  plugin with no declared endpoints.
</Callout>

## A generated skill contains no credentials and no commands

Read one and you will notice two absences. Both are deliberate.

**There is no authentication section.** The employee never authenticates. The
office attaches the key and signs the request, so a document telling the employee
how to build an auth header would be describing work it does not do.

**There are no shell commands.** No `curl`, no `fetch`, no scripts. An employee
calls a plugin as a tool, and an employee running on
[a machine you own](/docs/devices) has no shell in the office at all. A document
full of commands works in one place and fails in the other.

<Callout type="warn">
  **An older skill may still carry both.** Generated documents used to include an
  authentication section and command examples. If you are reading one that does,
  it was written under the previous behaviour. Regenerating it produces the
  current shape.
</Callout>

## The two ways an employee calls a plugin

### A named tool, when the plugin declares one

Every enabled endpoint on a plugin becomes a tool the employee can call by
name. The tool carries its own parameter schema, so the employee is working from
a documented contract rather than a guess.

**Prefer this wherever you can.** It is the difference between an employee that
knows an endpoint takes `invoiceId` in the path and one that is inferring it.

### `hos_plugin_request`, for everything else

A plugin with no endpoints declared is still fully callable. The employee
names the plugin and supplies a path, and the office does the rest:

```
hos_plugin_request({
  integration: "Acme Billing",
  method: "GET",
  path: "/v1/invoices/inv_7Kd2mQ",
  query: { expand: "customer" }
})
```

The office resolves the host, attaches the credential, signs the request and
sends it. The key never enters the conversation.

The argument that names the plugin is still called `integration`, the older word. It takes
the plugin's name or its ID. No [parameter defaults](/docs/plugins/settings) apply here,
because this tool has no declared parameters to fill.

<Callout>
  **The host is not a parameter.** An employee can only reach software you already
  connected. It cannot be talked into sending your credential somewhere else,
  because it never names a destination: it names one of your connections. The
  worst case is misuse of an API you chose to connect.
</Callout>

Two properties worth knowing:

**Query parameters go in `query`, not inside `path`.** For a plugin that
signs its requests, the query string is part of what gets signed, so a parameter
smuggled into the path is not covered by the signature.

**A name that is not connected is an error, not a guess.** If the employee asks
for a plugin this office does not have, the error lists the ones it does.

This works identically on a machine you own. The call is made by the office, so
no credential is copied to the device. See
[Tools your machine does not hold](/docs/devices/office-tools).

## Where the body came from matters

Every skill records a `contentSource`, which is about the **body** rather than
the origin:

| `contentSource` | Means | Protected from sync |
| --- | --- | --- |
| `generated` | Derived from documentation, unconfirmed | No |
| `manual` | Written or edited by a person | Yes |
| `verified` | Proven against the live API | Yes |

When a plugin syncs, it skips skills whose body is `manual` or `verified`.
A routine sync cannot discard a proven procedure or a human edit.

<Callout type="warn">
  **Editing a skill's body marks it `manual` automatically.** Sending `content`
  without setting `contentSource` stamps it, on the reasoning that a human edit
  is human authorship. That is usually what you want. It is a surprise if you did
  not expect it.
</Callout>

<Callout type="warn">
  **Regenerating replaces the body, and a `verified` stamp does not survive it.**
  Locking protects a skill from routine sync, not from an explicit regenerate. A
  `manual` body keeps its stamp and its wording is preserved, but a `verified` one
  drops to `generated`: the proof was about the previous text, and it does not
  carry over to text that has just been rewritten. Re-run verification to earn it
  back. A regenerate that fails changes nothing.
</Callout>

Only one route produces `verified`, and it is worth asking for. See
[Proving the skill is a separate ask](/docs/plugins/creating#proving-the-skill-is-a-separate-ask).

<Callout>
  **`verified` cannot be claimed, only earned.** There is no parameter that sets
  it. Publishing a skill resolves the stamp from whether a real call against a
  declared endpoint actually succeeded in that same cycle, so neither you nor an
  employee can assert it. If nothing was proven, the skill publishes as
  `generated` and says so in its own first line.
</Callout>

## Changing the credential does not rewrite the document

A plugin points at one or more secret groups, and each group supplies the
environment variables the office injects when it makes a call. Linking or
unlinking a group changes those variables straight away.

The skill is updated by halves, and the halves move at different times.

| What changes | When |
| --- | --- |
| The variables the office injects | Immediately |
| The list of variables the skill records | Immediately |
| The skill's own text | Only when you recompile |

The first two are derived from the connection every time it changes, so they are
never behind. The text is written by a compile, and linking a secret does not run
one.

<Callout type="warn">
  **Recompile after changing what is connected.** Until you do, the document can
  still describe the previous credential, and the document is what the employee
  reads. The console offers the rebuild at the moment you make the change. A
  compile also re-checks the text against what is really injected, and reports any
  variable it names that does not exist.
</Callout>

Because the credential changed, this is also the moment to prove the connection
again. A `verified` stamp was earned against the previous credential, and it says
nothing about the new one.

## When a skill and a connection disagree

They fail differently, and the difference tells you where to look.

| Symptom | Where the problem is |
| --- | --- |
| The employee calls an endpoint that does not exist | The skill. Its body describes something the API does not have |
| The employee calls the right endpoint and gets a `401` | The connection. Either the stored credential is rejected, or the authentication type on the plugin does not match what the API expects |
| A red warning on the plugin, saying a call failed | Neither, yet. The console recorded a real failure. Open the logs it links to and the response says which |
| The employee does not try at all | The skill. Its description did not match the task |
| The employee reports the plugin is not connected | The connection. It is not attached to this office |

Editing a skill to describe an endpoint does not make that endpoint reachable,
and deleting a skill does not revoke a credential.

## When a call fails, the console says so

Employees call plugins on their own, often while nobody is looking. So a
failed call is recorded rather than lost.

Every call an employee makes is logged against the plugin it used. A call
that returns an error, times out, or never reaches the host also marks the
plugin, and the console shows a warning on it with the response that came
back. **Anyone who can read the office is notified**, and the notification opens
that office's logs already filtered to the plugin.

The warning stays until someone marks it reviewed. Marking it reviewed records
that a person looked; it does not claim the plugin is fixed, and **the next
failure raises it again on its own**.

<Callout>
  **A busy plugin failing repeatedly will notify repeatedly today.** There
  is no cooldown yet. If that becomes noisy, tell us.
</Callout>
