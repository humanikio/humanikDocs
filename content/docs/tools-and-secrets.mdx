---
title: Tools and secrets
description: Connecting software an employee can use, and where its credentials live.
---

An AI employee reaches outside its office in two ways: **integrations**, which
connect it to software, and its **vault**, which holds the credentials those
integrations need.

The two are separate on purpose, and understanding why makes the rest obvious.

## An integration points at a secret. It does not hold one.

When you create an integration with credentials, the values do not go into the
integration. They are written into a **secret group** in a vault, and the
integration stores a reference to that group.

```
integration  ──references──▶  secret group  ──injected at boot──▶  the machine
```

Three things follow from that:

**No read endpoint returns a credential.** Listing integrations, reading one, or
listing its secret references all return names and pointers. There is exactly one
endpoint on the office surface that returns a decrypted value, and it needs a
separate permission.

**One secret can serve many integrations.** Rotating it is one write, not one per
integration.

**Removing an integration does not delete the credential.** The reference goes;
the group stays, still usable by anything else pointing at it.

## Two vaults, and the choice matters

A secret group lives in one of two places.

| | Office vault | Tenant vault |
| --- | --- | --- |
| Reaches | That one office | Any office pointed at it |
| Rotating it affects | One employee | Every employee using it |
| Good for | A credential only this employee should hold | A shared company account |

**Prefer the tenant vault for anything shared.** A Stripe key used by four
employees should be one group rotated once, not four copies rotated four times
and forgotten in a fifth place.

The tradeoff is blast radius. A tenant secret is reachable by every office
pointed at it, so the decision is about who should hold the credential, not about
convenience.

## Credentials are injected at boot

This is the behaviour that surprises people most often.

<Callout type="warn">
  **A secret is read when the office starts.** Adding, changing, or removing one
  does nothing to a running employee. If you change a value and behaviour does
  not change, the office has not restarted.
</Callout>

Restarting is a normal operation and takes effect immediately. It is worth
knowing about before you spend an hour debugging a key that was correct the whole
time.

## Two permissions, not one

Operating an office and reading its credentials are different rights.

| Action | Permits |
| --- | --- |
| `office:read` · `office:manage` | Running the office, attaching things to it |
| `secrets:read` · `secrets:write` | Reading and writing vault values |

Someone who can operate an employee does not automatically get to read the keys
it uses. Grant them separately, and grant `secrets:read` sparingly: it is the
one that returns plaintext.

## Templates: define once, use everywhere

An integration created directly on an office belongs to that office. If eight
employees all need the same connection, that is eight integrations to maintain.

The **tenant integration library** solves that. Define a template once, then
instantiate it into any office. The credential lives in the tenant vault, so a
rotation reaches every office using it.

Two operations connect an office to the library:

| Operation | Direction |
| --- | --- |
| **From template** | Library into an office |
| **Promote to template** | An office's integration back into the library |

<Callout type="warn">
  **Promotion is gated twice.** It requires `office:manage` on the office **and**
  a console scoped permission, because it writes into a shared library and mints
  a secret every office can be pointed at. An action that starts inside one
  boundary and lands in a wider one is checked at both ends.
</Callout>

## What an employee can see about its own access

`GET /offices/{officeId}/inherited-tenant-secrets` answers *what does this
employee actually have access to*, without exposing any value. It needs only
`office:read`.

It is the right endpoint for an audit, and it is worth running before widening
anything.
