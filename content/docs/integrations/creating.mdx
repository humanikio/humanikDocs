---
title: Creating an integration
description: Two ways to connect software to an employee, and when each one is the right choice.
---

[Integrations and secrets](/docs/integrations) covers what an integration is: a host, an
authentication scheme, a credential reference, and a list of endpoints that become tools.

This page is about getting one made. There are three routes to the same object, and the choice
comes down to one question: **do you already know the endpoints?**

## The short answer

| | Declare it yourself | Ask Nova in the console | Drive Nova from the API |
| --- | --- | --- | --- |
| **You provide** | Base URL, auth type, every endpoint | The name of the software, and a credential | The same, as a prompt |
| **Interface** | [`POST /offices/{officeId}/integrations`](/docs/api-reference/offices/integrations/createOfficeIntegration) | A conversation | [`POST /ai/run`](/docs/api-reference/nova/running-nova/runNovaCycle) |
| **Takes** | One call | A few minutes | A few minutes |
| **Endpoints are** | Exactly what you declared | Researched from the live documentation | The same |
| **Best when** | You have the API docs open | You want it working without reading them | You are provisioning offices programmatically |

Nova is the easier route and the one most people should use. Declaring it yourself is faster
when you already have the specification.

<Callout>
  **Nova is not console only.** The third column is the same workflow as the second, started
  with an API call instead of a message box. Nova acts as the caller who sent the prompt, under
  that caller's roles, so it can create nothing you could not have created yourself. See
  [How Nova is permissioned](/docs/api-reference/nova#how-nova-is-permissioned).
</Callout>

## Declaring it yourself

Create the integration with its endpoints in place:

```json
{
  "name": "Acme Billing",
  "baseUrl": "https://api.acme.com",
  "authType": "bearer",
  "credentials": { "API_KEY": "sk_live_..." },
  "tools": [
    {
      "toolName": "acme_get_invoice",
      "description": "Fetch one invoice by id",
      "method": "GET",
      "path": "/v1/invoices/{invoiceId}",
      "enabled": true,
      "parameters": {
        "invoiceId": {
          "type": "string",
          "required": true,
          "in": "path",
          "description": "The invoice id"
        }
      }
    }
  ]
}
```

`credentials` is required unless `authType` is `none`. The values go straight into the office
vault as a secret group and the integration is linked to it by reference, so one call sets up
the connection, the credential and the endpoints together. The employee can call
`acme_get_invoice` by name on its next boot.

To point an integration at a credential that already exists instead, use
[`POST /offices/{officeId}/integrations/{integrationId}/secret-refs`](/docs/api-reference/offices/integrations/addOfficeIntegrationSecretRef).

Adding or changing endpoints later is a
[`PATCH`](/docs/api-reference/offices/integrations/updateOfficeIntegration) on the integration.
The skill is rewritten from the updated record automatically, and the employee picks the tools
up on its next boot.

<Callout type="warn">
  **`tools` replaces the whole array. It does not merge.** Send the full set you want, because
  endpoints are declared as a set and a merge would leave no way to remove one. Omit the field
  to leave the existing endpoints alone.
</Callout>

<Callout type="warn">
  **Every parameter needs an `in`.** It says where the value goes on the wire: `path`, `query`,
  `header`, or `body`. A parameter without one is rejected with a `400` naming the field, rather
  than stored. A stored one would be dropped when the request was built: the call would go out
  missing that value and nothing would report it.
</Callout>

### Endpoints are the part that matters

An integration with no endpoints declared still works. It holds a credential and a host, and
the employee reaches it with `hos_integration_request`, supplying a path itself. See
[Integration skills](/docs/integrations/skills#the-two-ways-an-employee-calls-an-integration).

But nothing has told the employee what paths exist. Its skill is written from the integration
record, so with no endpoints to describe, the best it can offer is a plausible guess at what an
API of that kind usually looks like, marked as unconfirmed.

Declaring endpoints is what turns that into named tools with documented arguments. It is the
single highest value thing you can put in an integration.

## Having Nova build it

This is the route most people want. You describe the software, Nova does the research, and it
stops to check with you at the two points where your judgement is needed.

### What to say

Plain language is enough. Nova recognises the intent from any of these:

```
Connect Stripe to this office.

Set up an integration with SendGrid so this employee can send email.

I want to connect our internal billing API at https://billing.acme.internal.
```

The last one takes a different path from the first two, and the difference is just whether Nova
can find public documentation for the service.

| | Recognised service | Your own API |
| --- | --- | --- |
| **Nova does** | Looks up the API and proposes the setup | Asks you for the base URL, auth type, and credential field names |
| **You do** | Confirm, then supply the credential | Answer the questions, confirm, then supply the credential |

<Callout>
  **Nova does not guess your API.** For a service it cannot look up, it asks. If you are
  connecting something internal, have the base URL and the authentication type ready and the
  conversation is short.
</Callout>

### It stops twice, on purpose

Nova does not run the whole thing and tell you afterwards. It pauses at two points and waits.

<Steps>

<Step>
**Confirm the setup.** Nova summarises what it is about to create: the service, the base URL,
the authentication type, and what it will name things. Nothing is written until you accept.
</Step>

<Step>
**Supply the credential.** Nova sends you a secure form with the exact fields the service needs.
The value goes straight into the vault. It never passes through the conversation.
</Step>

</Steps>

<Callout type="warn">
  **Nova will never ask you to paste a key into the chat.** If anything appears to, that is
  worth reporting. Credentials are collected through the form so they do not end up in a
  transcript, in a message history, or in anything you later export.
</Callout>

After the second step Nova registers the integration, links the credential, and generates the
skill. The employee can use it on its next boot.

### Proving it works is a separate ask

Setup gives you a working integration whose skill is written from the service's documentation.
That skill is marked `generated`, meaning nobody has confirmed it against the live API.

Nova can go further, and it is worth asking:

```
Verify the Stripe skill against the real API.
```

Nova then reads the live documentation for the exact contract, fires a real authenticated
request, and checks the response contains what the contract promised. It publishes only if the
call confirms it, and the skill becomes `verified` and locked, so a routine sync cannot replace
it.

Each step appears in the chat as it runs, with the request, the response status, and whether the
assertion held. Nothing is published on a step that failed. Started from `/ai/run`, the same
trace is written to the chat the response names, so a programmatic caller can read back exactly
what was tried.

<Callout>
  **Your credential is never shown, to you or to the employee, in that trace.** Nova writes the
  request with a placeholder. The value is substituted server side at the moment the call goes
  out, and any occurrence of it in the response is masked before the trace is rendered.
</Callout>

### What verification cannot cover

It fires a real request, which makes it excellent for reads and unsuitable for writes.
Confirming a "create invoice" endpoint would mean creating an invoice.

So an integration can end up part proven: its reads confirmed, its writes documented but
untested. That is worth knowing when you read a skill, and it is the reason the stamp is worth
trusting where it appears.

## After it exists

Every route ends in the same place. The integration syncs to a **skill**, the document the
employee reads to know how to use the software. See
[Skills and protocols](/docs/skills-and-protocols) for how skills reach an employee and what
the verification stamp means.

The rest of the surface is documented under
[Integrations in the office reference](/docs/api-reference/offices/integrations/listOfficeIntegrations):
reading and updating one, managing its secret references, and the template operations covered
in [Integrations and secrets](/docs/integrations#templates-define-once-use-everywhere).
