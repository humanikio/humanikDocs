## What this reference covers

**The machine callable surface.** Every endpoint here can be called with an
`hsk_` API key. If it is documented in this section, your key can reach it,
assuming the service account holds the permission named on the endpoint.

Deliberately excluded:

| Not here | Why | Where instead |
| --- | --- | --- |
| Identity administration | Requires a signed in user. API keys are rejected. | [Access control](/docs/access-control) |
| Webhook receivers | Called by us, not by you | |
| Internal service routes | Between our own services | |

<Callout type="warn">
  **Identity administration is closed to API keys.** Every route under `/iam` and
  `/service-accounts` requires a signed in user, and returns `403` to a key even
  when the service account holds `iam:manage`. A machine identity that could mint
  machine identities, or grant itself a role, could escalate its own privileges
  with no person involved.
</Callout>

The practical split: **provisioning is a console step, operation is an API step.**
Create the service account and grant its roles once as a person, then the key
does the work. Start with
[Service accounts](/docs/access-control/service-accounts) if you do not have a
key yet.

## How permissions are shown

Every endpoint that carries a permission names it as an action at a scope:

```
office:manage @ workspace/{id}
```

That line tells you two things: which action your service account needs, and the
boundary its assignment has to cover. Both have to be true. A role granting
`office:manage` assigned at a different workspace will still be denied.

Scopes are `console`, `workspace/{id}`, and `office/{id}`.

<Callout>
  This reference tells you **which permission an endpoint needs**. It does not
  explain how roles, policies, and assignments fit together. That model is in
  [Access control](/docs/access-control), and it is worth reading once before
  granting anything.
</Callout>

## When a call is denied

A `403` names the action and resource it wanted:

```json
{
  "success": false,
  "error": "Forbidden",
  "message": "<decision reason>",
  "action": "office:manage",
  "resource": "workspace/ws_a1b2c3/office/off_dispatch"
}
```

Grant that exact pair rather than widening a role. See
[Granting access](/docs/access-control/assignments).
