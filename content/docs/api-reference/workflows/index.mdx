A workflow is a graph. One trigger step starts it, action steps run in order,
and one of those steps can hand work to an AI employee.

<ApiSetup />

<Callout>
  **New to this?** [Workflows](/docs/workflows) covers what a workflow is, when
  to draw one instead of asking an employee, and how triggering works.
  [Authoring a workflow](/docs/workflows/authoring) covers ordering,
  connections, step fields, and the `{{trigger.*}}` placeholders. This page
  assumes both and describes the API surface.
</Callout>

## The one thing to understand first

**Saving a graph is not saving a file.** A single
[Update a workflow](/docs/api-reference/workflows/workflows/updateWorkflow) call
that includes `canvas` will snapshot a version, compile the graph, and change
which events the workflow subscribes to. It is the operation that makes an
automation live, and everything else here is arranged around it.

Two consequences catch people out:

<Callout type="warn">
  **Activating takes `status` and `canvas` in the same request.** Bindings are
  only reconciled when a canvas is present, so sending `status: "active"` on its
  own updates the field and the workflow still will not fire.
</Callout>

<Callout type="warn">
  **An invalid graph saves without error.** The compile result is recorded
  rather than returned. Call
  [Get the compiled graph](/docs/api-reference/workflows/versions/getWorkflowIr)
  after any canvas save and check `valid`.
</Callout>

## Building one

<Steps>

<Step>
**Read the catalogue.**
[List node definitions](/docs/api-reference/workflows/node-definitions/listNodeDefinitions)
gives you every step's `id`, the fields it accepts, and what it emits. You need
this before you can write a canvas by hand.
</Step>

<Step>
**Create the draft.**
[Create a workflow](/docs/api-reference/workflows/workflows/createWorkflow)
takes a name and returns an empty workflow.
</Step>

<Step>
**Save the graph.**
[Update a workflow](/docs/api-reference/workflows/workflows/updateWorkflow) with
a `canvas`. Then check
[the compiled graph](/docs/api-reference/workflows/versions/getWorkflowIr) to
confirm it compiled.
</Step>

<Step>
**Test it.**
[Test fire a workflow](/docs/api-reference/workflows/runs/testWorkflow) runs it
once against a payload you supply, and works on a draft. Every action executes
for real, and only data source triggers can be tested this way.
</Step>

<Step>
**Activate.** Send `status: "active"` together with the canvas, then confirm
`subscribedNodeIds` is populated on the response.
</Step>

</Steps>

## Organising them

Workflows can be grouped into flat, unnested folders called collections. The
part that catches people out is that it takes two different endpoints, and
neither is called what you would guess.

| To | Call |
| --- | --- |
| Put a workflow in a collection | [Update a workflow](/docs/api-reference/workflows/workflows/updateWorkflow) with `collection` |
| Take it out | The same, with `collection: null` |
| Create an empty folder | [Register a collection name](/docs/api-reference/workflows/collections/addWorkflowCollection) |
| See which folders exist | [List collections](/docs/api-reference/workflows/collections/listWorkflowCollections) |
| See what is in one | [List workflows](/docs/api-reference/workflows/workflows/listWorkflows) and group by `collection` |

A workflow points at one folder by name, so there is no add-to-collection
endpoint and nothing to remove a workflow from. Setting the field is the whole
mechanism.

```bash
curl -X PATCH "$HOS_API/workspaces/ws_a1b2c3/workflows/wf_7Kd2mQ" \
  -H "Authorization: Bearer $HOS_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "collection": "Lead handling" }'
```

You do not need to register the name first. Registering matters when you want a
folder to survive its last workflow leaving, or to exist before anything is in
it.

<Callout>
  **Deleting a collection keeps the workflows.**
  [Delete a collection](/docs/api-reference/workflows/collections/removeWorkflowCollection)
  removes the name and clears it off everything that pointed at it, so those
  workflows become ungrouped rather than deleted.
</Callout>

## Tracking what is happening to one person

A run is a record of one workflow doing something, and that something is
usually happening to a person. Three calls make that side of it usable.

### Which contact a run is about

Every run carries `contactId`, and it is worth knowing when it gets set before
you rely on it.

**A run is started by a record, not by a contact.** A trigger fires on whatever
came in, and the contact is worked out later by whichever step resolves one,
such as a Find contact or Create contact step. That has two consequences:

- `contactId` is null until the first step has finished, so a run that failed at
  its trigger has no contact even when the incoming record plainly names
  someone.
- Some workflows never resolve a contact at all.

Null is therefore a normal answer rather than a missing value. When it is null,
fall back to `trigger.record`, which is the raw payload that started the run and
usually carries an email or a phone number. A run showing a real email that
never resolved to a contact is worth a second look, because it usually means a
lookup step did not match.

Going the other way, from a person to their workflows, use
[List a contact's workflow runs](/docs/api-reference/crm/contacts/listContactRuns).
Re entry is just another run, so that call doubles as an enrolment history.

### Why a run is paused, and when it will move

A run with `status: waiting` is paused at the step named by `waitingNodeId`, and
there are two quite different reasons for it. Read that step's entry in
`nodeResults` to tell them apart.

| Paused on | Looks like | Moves when |
| --- | --- | --- |
| A Wait step | a timer | its time is up |
| A Drip step | `outputs.queued: true` | its turn in the queue comes round |

The difference matters. A timer will fire on its own and you can predict when. A
Drip queue releases a fixed number of runs per interval, so a run can sit in one
for a long time, and how long depends on how many are in front of it.

For a queued run,
[Get a run's place in a queue](/docs/api-reference/workflows/runs/getRunQueuePosition)
answers that:

```bash
curl "$HOS_API/workspaces/ws_a1b2c3/workflows/wf_7Kd2mQ/runs/run_8Fs3Kd/queue-position" \
  -H "Authorization: Bearer $HOS_API_KEY"
```

```json
{ "success": true, "position": { "position": 3, "total": 1204, "claimed": false } }
```

The Drip step's own settings are in its `nodeResults` entry, so you can turn a
position into a time: `ceil(position / batchSize)` is the batch it is in, and
batches go out one `intervalSec` apart.

<Callout type="warn">
  **Treat that as an estimate.** Drip settings are read fresh every time the
  queue releases a batch, so raising the batch size moves everything still
  queued and invalidates any figure worked out before the change.
</Callout>

### Releasing one run early

[Advance a run](/docs/api-reference/workflows/runs/advanceRun) pushes a single
paused run past the step it is stuck on, whether that is a timer or a queue.

```bash
curl -X POST "$HOS_API/workspaces/ws_a1b2c3/workflows/wf_7Kd2mQ/runs/run_8Fs3Kd/advance" \
  -H "Authorization: Bearer $HOS_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "nodeId": "drip_1" }'
```

Send the run's own `waitingNodeId` as `nodeId`. Sending anything else returns
`409` rather than releasing the run.

<Callout type="warn">
  **This is one run, not the batch.** Releasing a run from a Drip queue moves
  that run only and leaves the queue's schedule untouched. Nobody else's place
  changes. There is no call that empties a queue, and that is deliberate: a Drip
  step exists to stop a large import firing everything at once, so a way to
  release all of it in one go would undo the only thing the step is there for.
</Callout>

If a Drip step is simply too slow, change the step instead. Settings are re
read on every release, so raising the batch size moves everyone still queued,
which is both faster and safer than releasing runs one at a time.

## Permissions

Two actions cover this surface, both scoped to the workspace in the path.

| Action | Reaches |
| --- | --- |
| `workflow:read` | Workflows, versions, the compiled graph, runs, queue positions, collections, node definitions |
| `workflow:manage` | Creating, saving, deleting, test firing, advancing a run, and collection changes |

`workflow:manage` includes test firing, which starts real runs with real side
effects. It is not a read-adjacent grant. It also covers advancing a run, which
sends whatever the next step does, so a released run can put a message in front
of a customer.

Reading a queue position is `workflow:read`, because it reports an order rather
than changing one.

Names and contact details on a run are **not** covered by either action. Runs
carry a `contactId` and nothing more, and resolving those ids needs
`contact:read` through
[Get many contacts by id](/docs/api-reference/crm/contacts/getContactsByIds).
That split is intentional, so workflow access does not quietly become contact
access.

## What is not here

**Triggers as standalone objects.** A workflow's bindings are derived from its
graph and reconciled on save. There is no endpoint to create one directly, by
design: the graph is the source of truth, and a binding that disagreed with it
would be unreachable.

**Starting a production run.** Runs begin from a real event or from
[Test fire a workflow](/docs/api-reference/workflows/runs/testWorkflow). There
is no general run endpoint.

**Restoring a version.** Snapshots are readable, and bringing one back means
reading its canvas and saving it again through
[Update a workflow](/docs/api-reference/workflows/workflows/updateWorkflow),
which stores it as a new version on top of the history.
