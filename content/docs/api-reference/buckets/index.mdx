A bucket is a named container for files inside a namespace. Every file in it has
a path, and the path is the address you act on.

<ApiSetup />

<Callout>

  page describes the API surface.
</Callout>

## The namespace is the unit of access

There are no per bucket or per file permissions. Two actions cover everything
here, both evaluated on the namespace in the path:

| Permission | Covers |
| --- | --- |
| `datasource:read` | Listing, reading, viewing a text file, listing versions, resolving a path, searching |
| `datasource:manage` | Creating, uploading, writing and editing text, replacing contents, restoring a version, moving, deleting |

Anyone who can read the namespace can read every bucket in it. If some documents
should be visible to one employee and not another, they belong in separate
namespaces. See [Datasource actions](/docs/access-control/actions#datasource).

**The namespace in the path scopes the row as well as the permission.** A bucket
or file belonging to a different namespace is reported as not found, even inside
the same tenant, and a missing row, another tenant's row and another namespace's
row are deliberately indistinguishable.

## The response says `asset`

The path says `object`. The response body says `asset`.

```
GET  .../objects/{objectId}   ->  { success, asset, signedUrl }
GET  .../objects              ->  { success, assets, total }
```

This is a partial rename that has not finished. Write clients against `asset`
and `assets`.

## Find by meaning, then act by path

This is the pattern the whole surface is built around, and it is worth following
rather than working around.

<Steps>

<Step>
#### Search for what you want

```bash
curl -X POST "$HOS_API/namespaces/ns_orders/buckets/$BUCKET/objects/search" \
  -H "Authorization: Bearer $HOS_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "query": "the Acme renewal from last year" }'
```

Every hit carries a `path`. Check `searchable` before reading `matches`: when
the namespace has file search turned off the call returns `200` with
`searchable: false` and an empty list, which is not an error.
</Step>

<Step>
#### Use the path you were given

```bash
curl -X POST "$HOS_API/namespaces/ns_orders/buckets/$BUCKET/objects/resolve" \
  -H "Authorization: Bearer $HOS_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "path": "/contracts/2026/acme-msa.pdf" }'
```

Use a path a call returned, not one you composed. Paths are case sensitive, and
if the exact match misses, a corrected match is reported through
`matchedInsensitively` and `object.path` is then the real one.
</Step>

</Steps>

## Browsing by folder

Folders are segments of a path, not separate resources. Send `delimiter=/` to
walk one level at a time.

```bash
curl "$HOS_API/namespaces/ns_orders/buckets/$BUCKET/objects?workspaceId=ws_a1b2c3&delimiter=/&prefix=/contracts/" \
  -H "Authorization: Bearer $HOS_KEY"
```

`assets` holds the files directly in `prefix`, and `delimitedPrefixes` holds the
folders below it. Call again with one of those as the new `prefix` to go deeper.
Omit the delimiter for a flat listing of everything underneath.

`folderCounts` gives the number of files below each folder at any depth, which is
what you want before telling someone how much a delete would remove.

## Changing a file: view, then edit with the version

A file's contents change in place. The id and path stay the same, `version` goes
up by one, and the previous contents are kept (the 20 most recent per file).
Every change says which version it was based on, so two writers cannot
silently overwrite each other.

<Steps>

<Step>
#### View it, and keep the version

```bash
curl "$HOS_API/namespaces/ns_orders/buckets/$BUCKET/objects/$OBJECT/text?workspaceId=ws_a1b2c3" \
  -H "Authorization: Bearer $HOS_KEY"
```

`content` is numbered lines (`     3\tStep 1: say hello`) and `version` is what
the next change must send back. Text files only; up to 2,000 lines per call, with
`more: true` when there is more.
</Step>

<Step>
#### Edit with that version

```bash
curl -X POST "$HOS_API/namespaces/ns_orders/buckets/$BUCKET/objects/$OBJECT/edits" \
  -H "Authorization: Bearer $HOS_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "ifVersion": 4,
    "edits": [
      { "type": "replace", "oldText": "Step 1: say hello", "newText": "Step 1: greet them by name" }
    ]
  }'
```

`oldText` must appear exactly once. The response carries the new `version`, so
further edits can follow without viewing again. A `409` means the file changed
since your version: view it again and redo the change.
</Step>

</Steps>

To create a text file, or replace one whole, use
[Write a text file](/docs/api-reference/buckets/editing/writeTextObject): it
refuses to overwrite an existing file unless you send its version. For any other
type, [Replace a file's contents](/docs/api-reference/buckets/editing/replaceObjectContent)
takes a multipart upload with `ifVersion`.

These operations answer errors with a stable `code` (`version_conflict`,
`exists`, `edit_failed` and others) next to the prose `error`, so a client can
branch on it.

## Three things that surprise people

**A download link is a capability.** [Get a file](/docs/api-reference/buckets/files/getObject)
returns a link valid for one hour, and anyone holding it can fetch the file
whether or not they have access to the namespace. Deleting the file does not
cancel it.

**A `200` does not guarantee a link.** If issuing it fails, the read still
returns `200` with the metadata and no `signedUrl`. Check for the field.

**`ready` does not mean searchable.** It means the file is stored, listable and
downloadable. A file uploaded while the namespace had file search turned off is
`ready` and unfindable, and turning the setting on later does not go back and
prepare it.

## What is not here

**Deleting a folder** removes every file under it and is not exposed to the API.
It is a console action, behind a confirmation naming the count.

**Reading a non-text file's text** (a spreadsheet as CSV, a Word document)
rather than downloading it is available to Nova through its own tools, not over
HTTP. Text files can be read over HTTP with
[View a text file](/docs/api-reference/buckets/editing/viewTextObject).

**Uploads are capped at 50 MB** and a larger file is rejected before the request
reaches the handler, so it returns a plain `500` rather than the usual envelope.
Check the size before sending.
