title: Bulletin permissions
description: Two grants. One is safe to give everybody, and it is the one that matters.
---

The bulletin has two permissions.

| Action | Covers |
| --- | --- |
| `bulletin:read` | See the board and the tiles on it |
| `bulletin:manage` | Everything that changes it |

Both sit at the workspace scope. For what an action is, how it is assigned, and
how a grant is evaluated, see [Access control](/docs/access-control). This page
says which grant each thing needs, not how grants work.

## Seeing a tile is not reading through it

This is the part worth reading twice, and it is why the read grant can be so
wide.

`bulletin:read` shows somebody the board: the tiles, their titles, their
arrangement. It does **not** give them the contents.

When a board is opened, each tile fetches its own data, and that fetch is
checked against the reader's own `datasource:read` on the
[namespace](/docs/namespaces) behind it. Somebody without it sees the tile and a
short note where the contents would be.

<Callout>
  Because of this split, `bulletin:read` is part of the baseline every member of
  a tenant holds. A person sees exactly the tiles they could have opened anyway,
  on a page that tells them what else exists. To close a board to somebody,
  remove the action in a custom role.
</Callout>

## Everything that writes is one grant

`bulletin:manage` covers posting a tile, changing or removing one, creating,
renaming, deleting and reordering boards, arranging a board into a page, and
pinning. Including tiles and boards somebody else made.

It is one tier rather than several because **nothing under it destroys data**:

- Deleting a board **un-groups** its tiles. They survive and need re-filing.
- Removing a tile removes a pointer. The table, file or bucket it addressed is
  untouched.
- Arranging a page can be rolled back to an earlier version.

Splitting that into contribute, edit, and administer was drawing three
boundaries around a loss that cannot happen.

Two things under it are still worth knowing before you hand it out, because they
change what **other people** see rather than what exists:

- **Pinning** promotes a tile to the top of a board for everyone who opens it.
- **Board order** decides which board the whole workspace lands on.

Neither loses anything, and both are visible to everybody immediately.

When an edit changes a tile's content, the tile records who made the change
alongside who posted it. The original author stays as the byline, because the
post is still theirs, and the edit is shown next to it.

## Editing in the console

The console puts every write behind a single **Configure** button, so one grant
gates all of it:

| In the console | Needs |
| --- | --- |
| Opening the bulletin, switching boards, reloading | `bulletin:read` |
| Contents inside a tile | `datasource:read` on that tile's namespace |
| **Configure**, and every tab inside it | `bulletin:manage` |
| Adding a tile, editing one, removing one | `bulletin:manage` |
| Creating, renaming, and reordering boards | `bulletin:manage` |
| Arranging a board's page | `bulletin:manage` |

Somebody with `bulletin:read` alone sees the board and a reload control, and no
Configure button. The controls are not disabled, they are absent: a person is
not shown a door they cannot open.

Somebody with neither sees no bulletin at all. The section is skipped rather
than showing an error about a feature they were never offered.

<Callout type="warn">
  **There is no pin control in the console.** Pinning works through the API and
  for AI employees; in the console it is not yet surfaced.
</Callout>

## Agents and API keys

An AI employee acting on the bulletin is gated on the same two actions as a
person, evaluated against its own assignments rather than the assignments of
whoever asked it. An employee without `bulletin:manage` cannot change a tile
because somebody asked it to.

An office employee holds both by default. Its tools are narrower than its
grant on purpose: it can read the board and post to it, and arranging or
deleting is left to a person in the console.

API keys carry grants the same way. See
[Authentication](/docs/authentication).
