---
title: Bulletin permissions
description: Four grants, split so a board can be shared widely without widening access to data.
---

The bulletin has four permissions, and they are deliberately not one. The split
lets you hand a board to everybody while keeping the ability to rearrange it,
and to decide what the whole workspace sees first, in fewer hands.

| Action | Covers |
| --- | --- |
| `bulletin:read` | See the board and its tiles |
| `bulletin:post` | Put a tile on the board |
| `bulletin:edit` | Change or remove tiles, create and rename boards, arrange a page |
| `bulletin:manage` | Pin a tile, and roll a page back to an earlier version |

All four sit at the workspace scope. For what an action is, how it is assigned,
and how a grant is evaluated, see
[Access control](/docs/access-control). This page says which grant each thing
needs, not how grants work.

## Seeing a tile is not reading through it

This is the part worth reading twice.

`bulletin:read` shows somebody the board: the tiles, their titles, their
arrangement. It does **not** give them the contents.

When a board is opened, each tile fetches its own data, and that fetch is
checked against the reader's own `datasource:read` on the
[namespace](/docs/namespaces) behind it. Somebody without it sees the tile and a
short note where the contents would be.

<Callout>
  Because of this split, `bulletin:read` can be granted broadly without
  widening anybody's reach into your data. A person sees exactly the tiles they
  could have opened anyway, on a page that tells them what else exists.
</Callout>

## Posting and editing are separate on purpose

`bulletin:post` lets somebody contribute without being able to disturb what is
already there. It is the grant for a team that should be able to put things up.

`bulletin:edit` covers changing and removing tiles, **including tiles somebody
else posted**. It also covers creating boards, renaming them, moving tiles
between them, and arranging a board's page.

When an edit changes a tile's content, the tile records who made the change
alongside who posted it. The original author stays as the byline, because the
post is still theirs, and the edit is shown next to it.

## Pinning is above editing

`bulletin:manage` covers pinning, because a pinned tile leads the page for
everyone who opens that board. Deciding what the workspace sees first is a
different kind of decision from arranging a page, so it takes a different
grant.

<Callout type="warn">
  **Board order does not currently require `bulletin:manage`.** Reordering
  boards changes which board the whole workspace lands on, and it is presently
  covered by `bulletin:edit`. If you are handing out `bulletin:edit` widely,
  know that it includes this.
</Callout>

## Editing in the console

Everything above applies the same way in the console as through the API. The
grant decides what appears.

The console puts every write behind a single **Configure** button, so one grant
gates all of it:

| In the console | Needs |
| --- | --- |
| Opening the bulletin, switching boards, reloading | `bulletin:read` |
| Contents inside a tile | `datasource:read` on that tile's namespace |
| **Configure**, and every tab inside it | `bulletin:edit` |
| Adding a tile, editing one, removing one | `bulletin:edit` |
| Creating, renaming, and reordering boards | `bulletin:edit` |
| Arranging a board's page | `bulletin:edit` |

Somebody with `bulletin:read` alone sees the board and a reload control, and no
Configure button. The controls are not disabled, they are absent: a person is
not shown a door they cannot open.

<Callout type="warn">
  **`bulletin:post` and `bulletin:manage` are API grants today.** The console
  has no separate add-a-tile path and no pin control, so somebody holding
  `bulletin:post` alone sees a read-only board there. Both actions work
  normally through the API and for AI employees.
</Callout>

## Agents and API keys

An AI employee acting on the bulletin is gated on the same four actions as a
person, evaluated against its own assignments rather than the assignments of
whoever asked it. An employee without `bulletin:edit` cannot edit a tile
because somebody asked it to.

API keys carry grants the same way. See
[Authentication](/docs/authentication).
