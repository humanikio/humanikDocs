A service account is a machine identity inside your tenant. It holds role
assignments exactly as a person does, and it is evaluated by the same policy
engine. An API key is a credential issued against one.

This page covers creating one and issuing its keys.
[Authentication](/docs/authentication) covers using a key once you have it: the
key format, how to send it, and how revocation behaves.

<Callout type="warn">
  Every endpoint on this page requires a **signed in user**. API keys are
  rejected before any permission is checked. See
  [How access control works](/docs/access-control).
</Callout>

## Creating one in the console

This is the path most people take. It is also the only path available if you do
not already hold a key, because a key cannot create a key.

Everything below lives in the console under **Organization** in the left
sidebar.

<Steps>

<Step>

### Create the identity

Go to **Organization → Service Accounts**, then **New service account**. Give it
a name and an optional description.

Name it after the job it does, not the person who set it up. The name is what you
will read in an audit trail six months from now.

</Step>

<Step>

### Grant it permissions

Open the account you just created. Role assignments are managed here, not at
creation time.

Add one assignment per thing the account needs to reach. An assignment is a role
paired with the resource it applies to:

| Role | Resource | What it permits |
| --- | --- | --- |
| `viewer` | `workspace/ws_a1b2c3/namespace/ns_orders` | Read that one namespace |
| `editor` | `workspace/ws_a1b2c3` | Read and write across that workspace |

Grant the narrowest resource that still lets the job run. Widening later is one
edit. Discovering a machine had more reach than you thought is an incident.

<Callout type="warn">
  A service account has **only** what you assign here. It cannot inherit from a
  workspace, and it can never satisfy the owner bypass that a tenant owner gets.
  A missing assignment means denied, not degraded.
</Callout>

</Step>

<Step>

### Mint a key

On the same page, choose **Create API Key**. Give it a name that identifies what
will use it, so it can be rotated later without guesswork.

The full key is shown **once**. Copy it into your secret store before closing the
dialog. There is no way to see it again.

</Step>

<Step>

### Store it and make a request

Put the key and the base URL in your environment rather than in code. Every
example across these docs assumes these two names, so exporting them once makes
the rest copy runnable.

<ApiSetup />

The key is the **full** value, both halves joined by a dot: the `hsk_` access key
ID identifies it and the `hss_` secret authenticates it. Send it as a bearer
token:

```bash
curl "$HOS_API/offices?workspaceId=ws_a1b2c3" \
  -H "Authorization: Bearer $HOS_KEY"
```

A successful call returns the envelope used everywhere:

```json
{
  "success": true,
  "offices": [
    { "id": "off_9c1e7d", "name": "Dispatch", "status": "running" }
  ]
}
```

If this returns `403`, the key authenticated but the assignment in step 2 does
not cover what you asked for. The response body names the action and resource it
wanted. Add that exact pair and try again.

If it returns `401`, the key itself was not accepted. See
[Authentication](/docs/authentication#authentication-failures).

</Step>

</Steps>

### Where the related screens are

| Screen | Location | What it does |
| --- | --- | --- |
| Service Accounts | **Organization → Service Accounts** | Create identities, assign roles, mint and revoke keys |
| IAM | **Organization → IAM** | Define roles and policies. Tabs for Roles, Policies, and Hierarchy. |
| Members | **Organization → Members** | The same thing for people rather than machines |

Roles and policies are defined once under IAM and then assigned in either place.
A role means the same thing whether it is held by a person or a machine, which is
what makes the two screens mirror images of each other.

## Endpoint reference

All endpoints are scoped to `console`:

| Group | Permission |
| --- | --- |
| Reads | `iam:read` @ `console` |
| Writes | `iam:manage` @ `console` |

`401`, `403`, and `429` behave the same everywhere and are not repeated per
endpoint. See [Responses and errors](/docs/responses) and
[Rate limits](/docs/rate-limits).

## Endpoints

| Method | Path | Permission | Purpose |
| --- | --- | --- | --- |
| `POST` | `/service-accounts` | `iam:manage` | Create an identity |
| `GET` | `/service-accounts` | `iam:read` | List identities |
| `GET` | `/service-accounts/{saId}` | `iam:read` | Read one identity |
| `PUT` | `/service-accounts/{saId}` | `iam:manage` | Update name, description, assignments |
| `DELETE` | `/service-accounts/{saId}` | `iam:manage` | Delete the account and its keys |
| `POST` | `/service-accounts/{saId}/keys` | `iam:manage` | Mint a key |
| `GET` | `/service-accounts/{saId}/keys` | `iam:read` | List keys, sanitised |
| `PATCH` | `/service-accounts/{saId}/keys/{keyId}` | `iam:manage` | Rename, activate, deactivate |
| `DELETE` | `/service-accounts/{saId}/keys/{keyId}` | `iam:manage` | Delete a key |

## Accounts

### `POST /service-accounts`

Create a machine identity.

| | |
| --- | --- |
| **Permission** | `iam:manage` @ `console` |
| **Idempotent** | No. Each call creates a new account. |

#### Request body

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `name` | `string` | **Yes** | Display name |
| `description` | `string` | No | |
| `roleAssignments` | `array` | No | `{ roleId, resource }` pairs. This is the entire permission set of the account. |
| `subjectRef` | `object` | No | What the machine represents. **Immutable once set.** |

`subjectRef` is a discriminated union on `type`:

```json
{ "type": "office",  "workspaceId": "ws_a1b2c3", "officeId":  "off_dispatch" }
{ "type": "browser", "workspaceId": "ws_a1b2c3", "browserId": "bwr_a1b2c3d4" }
```

Omit it for an account that represents nothing in particular.

#### Request

```bash
curl -X POST "$HOS_API/service-accounts" \
  -H "Authorization: Bearer $HOS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Nightly reconciliation",
    "description": "Reads the orders namespace on a schedule",
    "roleAssignments": [
      { "roleId": "viewer", "resource": "workspace/ws_a1b2c3/namespace/ns_orders" }
    ]
  }'
```

<Callout>
  You will rarely call this. Office and browser service accounts are minted
  automatically when the office or browser is created. Manual creation is for
  machines that represent nothing in particular.
</Callout>

<Callout type="warn">
  `roleAssignments` is the account's **entire** permission set. It runs through
  the same evaluator a person's assignments do, and a service account can never
  satisfy the owner bypass. An omitted or wrong assignment means denied, not
  degraded.
</Callout>

### `PUT /service-accounts/{saId}`

Update name, description, or role assignments.

| | |
| --- | --- |
| **Permission** | `iam:manage` @ `console` |
| **Idempotent** | Yes. Replaces the fields you send. |

<Callout type="warn">
  `subjectRef` cannot be updated. It is set at creation only. A credential cannot
  be repointed at a different office or browser after it is issued, which is what
  stops a low value machine identity being quietly promoted to a high value one.
</Callout>

### `DELETE /service-accounts/{saId}`

Deletes the account and every key issued against it. Read the revocation timing
note under [key deletion](#delete-service-accountssaidkeyskeyid) before relying
on this to cut off access.

## Keys

### `POST /service-accounts/{saId}/keys`

Mint a key against an existing service account.

| | |
| --- | --- |
| **Permission** | `iam:manage` @ `console` |
| **Idempotent** | No. Each call mints a new key. |

#### Request body

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `name` | `string` | **Yes** | Label, so a key can be rotated without guessing what uses it |
| `expiresAt` | `string` | No | ISO 8601. Absent means the key does not expire. |

#### Request

```bash
curl -X POST "$HOS_API/service-accounts/sa_7f3b2a/keys" \
  -H "Authorization: Bearer $HOS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{ "name": "reconciliation-runner", "expiresAt": "2027-01-01T00:00:00Z" }'
```

#### Response `201 Created`

| Field | Type | Description |
| --- | --- | --- |
| `accessKeyId` | `string` | `hsk_` followed by 40 hex characters. Identifies the key. Safe to log. |
| `secret` | `string` | `hss_` followed by 64 hex characters. **Returned once and never again.** |
| `fullKey` | `string` | `hsk_....hss_...`. This is what a caller sends. |
| `apiKey` | `object` | The stored record, without the secret |

```json
{
  "success": true,
  "accessKeyId": "hsk_4f8a2b1c9d7e3a05f6b8c2d4e1a7f9b3c5d8e0a2",
  "secret": "hss_...",
  "fullKey": "hsk_4f8a....hss_...",
  "apiKey": {
    "id": "hsk_4f8a...",
    "name": "reconciliation-runner",
    "secretLastFour": "9b3c",
    "active": true,
    "usageCount": 0
  }
}
```

<Callout type="warn">
  **Capture `fullKey` on this response.** The secret is stored encrypted and only
  `secretLastFour` can be read back. There is no reveal endpoint. Losing it means
  minting a new key, not recovering this one.
</Callout>

### `GET /service-accounts/{saId}/keys`

List keys for an account, sanitised. No secret, encrypted or otherwise, is
returned.

| | |
| --- | --- |
| **Permission** | `iam:read` @ `console` |

Each row carries `secretLastFour`, `active`, `expiresAt`, `createdAt`,
`lastUsedAt`, and `usageCount`.

`lastUsedAt` and `usageCount` are the audit surface. A key with no recent use is
a candidate for deletion. A key with unexpected use is worth investigating.

### `PATCH /service-accounts/{saId}/keys/{keyId}`

| | |
| --- | --- |
| **Permission** | `iam:manage` @ `console` |
| **Idempotent** | Yes |

| Field | Type | Description |
| --- | --- | --- |
| `active` | `boolean` | Deactivate without deleting |
| `name` | `string` | Rename |

Deactivation is the reversible half of revocation. Prefer it when you are not
certain what a key serves.

### `DELETE /service-accounts/{saId}/keys/{keyId}`

Permanent.

| | |
| --- | --- |
| **Permission** | `iam:manage` @ `console` |

<Callout type="warn">
  **Revocation is not immediate.** Validated keys are cached for **five minutes**.
  A deleted or deactivated key can keep authenticating until that cache expires.
</Callout>

Every machine to machine call in the platform validates against this path, and
the cache protects it. The consequence is that five minutes is the revocation
window, and for a leaked credential that is the number that matters. Treat
rotation as the primary control and revocation as the follow up.

## Errors

Beyond the shared `401`, `403`, and `429`:

| Status | When |
| --- | --- |
| `400` | `name` is missing, or `subjectRef` is malformed |
| `403` | An API key was used. Identity administration requires a signed in user. |
| `404` | No such account or key, or it belongs to another tenant |
| `500` | The write failed |

Cross tenant reads return `404` rather than `403`. A resource that does not
exist and a resource you may not see are deliberately indistinguishable.
