---
title: The steps
description: Every step a workflow can take, and what each one is for.
---

A workflow is built from steps. This page covers what each one does and when to
reach for it.

It deliberately does not list the settings each step accepts. Those come from the
catalogue, which is generated from the running platform and is always current:
[List node definitions](/docs/api-reference/workflows/node-definitions/listNodeDefinitions)
returns every step with its fields, their types, and which are required. Read
this page to decide *which* step you want. Read the catalogue to fill it in.

## Starting steps

Every workflow declares exactly one, and it is what binds the graph to a real
source of events.

| Step | Starts a run when |
| --- | --- |
| **Data Source Trigger** | a record arrives at one of your data sources |
| **Calendar Event Booked** | an event is newly booked on one of your calendars |

A trigger that names no source binds to nothing rather than to everything, so a
half configured trigger is inert instead of dangerous.

### Narrowing a calendar trigger

By default every appointment on the chosen calendar starts the workflow,
including one the host typed straight into Google or Outlook. Two settings
narrow that.

**Which bookings** scopes the trigger to a single [booking
page](/docs/calendars/booking-links), so "someone booked a Discovery Call" and
"someone booked a support slot" can run different workflows on one calendar. An
appointment created outside a booking page has no page to match, so a scoped
trigger skips it.

Only reusable pages are offered here. A one-time link stops working after its
single booking, so a workflow bound to one could run at most once and would then
be quietly dead forever.

**Event name contains** matches text in the appointment title instead, which is
the one to reach for when the appointments come from somewhere other than a
booking page. Set both and both must match.

### What a booking hands the workflow

Appointments booked through a booking page carry the booker's answers, so later
steps can use them without asking again:

- `{{trigger.bookerName}}`, `{{trigger.bookerEmail}}`, `{{trigger.bookerPhone}}`
- `{{trigger.form.<question>}}` for anything else the page asks, custom
  questions included. A page asking "What would you like to cover?" under the
  key `notes` gives you `{{trigger.form.notes}}`
- `{{trigger.bookingLinkName}}` for the page it came through

These are the natural inputs to **Find Contact** and **If/Else**: look the
person up by `{{trigger.bookerEmail}}`, then branch on an answer they gave.

An appointment created directly in Google or Outlook has none of this, because
nobody filled a form in. A custom question also resolves empty on a page that
does not ask it, so branch on the answer rather than assuming it is there.

## Messaging

| Step | Does |
| --- | --- |
| **Send SMS** | text a contact from one of your workspace numbers |
| **Send Email** | email a contact from one of your domain addresses |
| **Notify User** | text a member of your team at the number in their settings |

Notify User is the odd one of the three, and the distinction matters: it messages
**your team**, not the contact the workflow is about. Use it for internal
handoffs such as telling a rep that a lead came in.

<Callout>
  **Placeholders resolve against the recipient.** In Send SMS and Send Email you
  can write `{{contact.first_name}}` without naming which contact, because these
  steps know who they are sending to. On other steps that placeholder only
  resolves once an earlier step has identified a contact.
</Callout>

## Contacts

| Step | Does |
| --- | --- |
| **Create Contact** | create one, reusing an existing match on the same phone or email |
| **Find Contact** | look one up. Creates nothing |
| **Update Contact** | change fields on a contact that already exists |
| **Add Tag** | apply tags, creating any that are new to the workspace |
| **Remove Tag** | remove specific tags, or clear them all |
| **Add Note** | put a timestamped note on the contact's timeline |

**Find Contact never creates or edits anything**, so a miss costs nothing. It
tries the contact id, then the phone, then the email, and stops at the first
one that matches.

By default it carries on in a single line whether or not it found anyone, and
you read the result downstream as `{{found}}`. That suits the common case,
which is "attach the contact if we have one", and it keeps a graph that only
needed a lookup from growing a fork it never uses.

Turn on **Split the path on the result** when you genuinely want two paths.
The step then grows Found and Not found exits, and "we already know this
person" and "this is new" become branches you draw rather than a condition you
write.

<Callout type="warn">
  **The exits only exist while that setting is on.** Turning it off removes
  them, and any lines already wired to Found or Not found are dropped with
  them. Turn it on before you draw those lines.
</Callout>

You may also see **Find Contact (Split)** in the step library, sitting at the
end of the Contacts group in grey. It is the older version of this step, from
before the setting above existed, and it always branches. It still runs, so
workflows built on it keep working and nothing needs migrating. Reach for Find
Contact for anything new.

<Callout>
  **The current contact.** Once any step identifies a contact, every later step
  can refer to it as `{{contact.*}}` without naming that step. The most recent
  one wins. This is why a Find Contact or Create Contact near the top of a graph
  makes everything after it simpler to write.
</Callout>

## Deals

| Step | Does |
| --- | --- |
| **Create Opportunity** | open a deal in a pipeline stage |
| **Find Opportunity** | look one up by id, or take the contact's most recent |
| **Update Opportunity** | move stages, mark won or lost, change fields |
| **Add Opportunity Note** | add a note to a deal |
| **Update Opportunity Note** | rewrite an existing deal note |

Find Opportunity always splits the path, with Found and Not found exits. Unlike
Find Contact it has no setting to turn that off.

## Working with your data

| Step | Does |
| --- | --- |
| **Run SQL** | query or change a database namespace, and use the result in later steps |

This is the step for a question the other steps cannot answer. A lookup in a
table you built yourself, a total across rows, a write into your own schema. It
runs against one namespace that you pick on the step, and it can only reach
tables in that namespace.

It splits the path when you turn on **Split the path on whether anything came
back**, giving you Rows and No rows exits. Left off, it has one way out and you
read the row count downstream instead.

### Values go in a separate field

The statement is fixed text. Anything that changes per run goes in the step's
**Values** field, as a JSON object, and the statement reads it back from a
relation called `input`:

```
Values:  { "email": "{{trigger.email}}" }

SELECT id, plan FROM customers
WHERE email = (SELECT payload->>'email' FROM input)
LIMIT 1
```

<Callout type="warn">
  **A `{{ }}` reference pasted into the statement itself is refused.** It would
  put whatever a webhook sent into the middle of your SQL, where a stray quote
  changes what the statement means. The Values field passes the same information
  in as a value, which cannot happen. The step will not save with a reference in
  the statement, and the editor will not let you apply one.
</Callout>

### Test it before it counts

The statement has to run once, successfully, before the step will accept it. The
test executes against your real data and then undoes itself, so a wrong column
name fails while you are looking at it rather than on the first live record.

Change a character afterwards and the step asks you to run it again. That is on
purpose: the thing that was proven is the exact text, not the general idea.

### What you can and cannot run

SELECT, INSERT and UPDATE. An UPDATE has to have a WHERE clause.

DELETE, DROP and TRUNCATE are refused here for the same reason they are refused
everywhere in the product. CREATE and ALTER are refused in this step
specifically: a table has to be created in the console so the namespace knows
about it, and one made here would be invisible to the table list. See
[Running SQL](/docs/namespaces/sql) for the whole picture, including the editor
you can build a statement in first.

A write returns nothing unless you add `RETURNING`. Without it you get a count
of rows changed and nothing else.

## Asking an employee

| Step | Does |
| --- | --- |
| **Prompt Office** | hand the work to an AI employee |

This is the step that puts judgement inside an otherwise fixed sequence. The
mechanical parts stay predictable and the decision happens exactly where you
put it.

<Callout type="warn">
  **The handoff is one direction.** The workflow hands the work over and carries
  straight on to the next step without waiting. The employee's reply lands in its
  own conversation rather than coming back as a value later steps can read. Design
  everything after this step so it does not depend on what the employee said.
</Callout>

## Controlling the flow

These five decide what runs, and when.

| Step | Does |
| --- | --- |
| **If / Else** | take one path or another based on the data |
| **Random Split** | take one of up to five paths at random |
| **Wait** | pause for a fixed length of time |
| **Wait for Appointment** | pause until a set time relative to a booking |
| **Drip** | let a few contacts through at a time |

### If / Else against Random Split

Both split the path. They are not alternatives to each other.

**If / Else** decides using the data: the amount, the stage, a field on the
contact. Give it the same input twice and it goes the same way twice.

**Random Split** decides by chance. You set the share each path receives, up to
five paths totalling one hundred percent, and each contact is assigned to one.
A path can be set to zero percent, which is how you hold a group back while
keeping it wired.

Use Random Split for A/B tests, for trying two versions of a message against each
other, or for spreading contacts evenly across paths.

<Callout>
  **A contact keeps the path it was given.** If the same contact comes back
  through the same Random Split later, it goes down the same path as before
  rather than being drawn again. Without that, someone entering twice would land
  in both halves of your test and the result would mean nothing.
</Callout>

To branch on whether a contact exists, use Find Contact with its split turned
on, rather than either of these.

### Wait against Drip

Both pause the workflow, and confusing them is the easiest mistake to make here.

**Wait is a delay.** Every contact pauses for the same length of time. Ten
contacts arriving together all wait three days, then all continue together.

**Drip is a rate limit.** Contacts queue and leave a few at a time. You set how
many are released and how often. Ten contacts at two per hour means the first two
leave immediately and the last two leave four hours later. How long any one
contact waits depends on how many arrived before it.

Reach for Drip when a burst would overwhelm something downstream: a bulk import
that would otherwise send hundreds of messages at once, or an employee that
cannot handle every request in the same minute.

<Callout>
  **Waiting is free.** Nothing runs while a workflow is paused, whether it is
  waiting three minutes or three weeks, and nothing is consumed. There is no cost
  pressure to compress a follow up.
</Callout>

Contacts leave a Drip in the order things actually happened, using the timestamp
on the record that started each run where the source provides one, rather than
the order the runs happened to be processed in.

<Callout type="warn">
  **Check the drain time before you save a Drip.** Releasing one contact per day
  means a hundred waiting contacts take a hundred days to clear. The setting that
  produces that is one dropdown away from a reasonable one. If you get it wrong,
  changing the numbers afterwards does apply to everyone still queued, so it is
  recoverable.
</Callout>

## Which steps identify a contact

Worth knowing, because it decides where `{{contact.*}}` will resolve:

Create Contact, Find Contact, Update Contact, Add Tag, and Remove Tag all
identify the contact they acted on, and every step after them can use it. A
trigger does not. A record arriving from a webhook carries whatever fields the
source sends, which is not the same as a contact in your CRM, so a workflow that
needs one has to Find or Create it first.

## Which steps split the path

**If / Else**, **Random Split** and **Find Opportunity** always do. **Find
Contact** and **Run SQL** do only while their split is turned on, and **Find
Contact (Split)**, the older step, always does. Each has named exits, and a line
leaving one has to say which exit it comes from. Every other step has a single
way out.

An exit you leave unconnected simply ends that branch. That is allowed, and it is
how you write "do nothing in this case".
