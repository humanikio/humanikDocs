---
title: Rate limits
description: Request limits, the headers that report them, and how to back off.
---

Some operations carry their own request limit, and the API reference page for each one says
so. This page covers what a limited call returns, the headers that report the limit, and how to
back off. What every other error status means is on
[Responses and errors](/docs/responses).

## What a request sees

| Situation | Result |
| --- | --- |
| The operation has a limit and you are under it | The normal response, with `X-RateLimit-Limit` and `X-RateLimit-Remaining` |
| The operation has a limit and you are over it | `429`, with a `Retry-After` header and `retryAfter` in the body, both in seconds |

## Headers

Operations that carry a limit return these headers:

| Header | Meaning |
| --- | --- |
| `X-RateLimit-Limit` | The ceiling being applied |
| `X-RateLimit-Remaining` | Requests left before the limit is reached |
| `Retry-After` | Seconds to wait. Sent only on a `429`. |

## When you are limited

```json
{
  "success": false,
  "error": "Rate limit exceeded",
  "message": "Too many requests. Please retry after 12 seconds.",
  "retryAfter": 12,
  "timestamp": "2026-08-02T14:03:11.204Z"
}
```

Wait for `retryAfter` seconds before retrying. It is authoritative, so prefer it
over a fixed backoff schedule.

## Staying under the limit

- Read `X-RateLimit-Remaining` and slow down before you hit zero, rather than
  waiting for a `429`.
- Retry `429` and `500` with exponential backoff and jitter. Do not retry `400`,
  `401`, `403`, or `404`, since none of them will succeed unchanged.
- Cache reads that do not change often. Office and workspace listings are
  usually stable between calls.
