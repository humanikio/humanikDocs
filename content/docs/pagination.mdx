title: Pagination
description: The paging shapes lists use, how to tell when you have the last page, and how to pull every record.
---

Lists return a bounded number of records at a time. This page covers the shapes a
paged list can take, the signal that says you have the last page, and a loop that
pulls every record. Each operation's own page in the
[API reference](/docs/api-reference) says which shape it uses and its largest
page size.

## The shapes

Not every list pages the same way. Read the operation's page, then use the stop
signal for its shape:

| The list returns | Send back for the next page | You have the last page when |
| --- | --- | --- |
| `nextCursor` | `cursor` set to that value | `nextCursor` is `null` |
| `cursor` and `hasMore` | `cursor` set to that value | `hasMore` is `false` |
| `hasMore`, with records that each have an `id` | `startAfter` set to the last record's `id` | `hasMore` is `false` |
| A page of records, on some lists that accept `offset` | `offset` raised by the number of records you got | A page comes back with fewer records than you asked for |

Some lists are not paged at all because they are bounded by design, such as the
nodes in one workflow. Those operations say so, and they return every record in
one call.

## Raise the page size first

Paged lists accept `limit`. The default is small because most callers are
rendering a screen, but a program pulling records should ask for the largest page
the operation allows.

```bash
curl "$HOS_API/workspaces/ws_a1b2c3/workflows/wf_x7y8z9/runs?limit=100" \
  -H "Authorization: Bearer $HOS_KEY"
```

Values above the maximum are clamped to the maximum rather than rejected. The
maximum is stated on each operation, because it differs by resource.

<Callout type="warn">
  A bigger page is not a substitute for paging. There is no value of `limit`
  that returns every record, so a caller that only raises `limit` stops at the
  maximum and reports a partial set as complete.
</Callout>

## Page past it with the cursor

On a list that returns `nextCursor`, pass it back as `cursor` to get the
following page.

```json
{
  "success": true,
  "runs": [{ "runId": "run_a1b2c3" }],
  "nextCursor": "eyJzIjoxNzU2MDkyODAwMDAwfQ"
}
```

```bash
curl "$HOS_API/workspaces/ws_a1b2c3/workflows/wf_x7y8z9/runs?limit=100&cursor=eyJzIjoxNzU2MDkyODAwMDAwfQ" \
  -H "Authorization: Bearer $HOS_KEY"
```

**`nextCursor` is `null` on the last page.** That is the signal to stop, and it
is the only reliable one on these lists. A short page does not mean the end, and
neither does an empty one.

## Pulling every record

Loop until the stop signal for the list's shape. For a `nextCursor` list:

```js
async function fetchAllRuns(workspaceId, workflowId) {
  const runs = []
  let cursor = null

  do {
    const params = new URLSearchParams({ limit: '100' })
    if (cursor) params.set('cursor', cursor)

    const res = await fetch(
      `${process.env.HOS_API}/workspaces/${workspaceId}/workflows/${workflowId}/runs?${params}`,
      { headers: { Authorization: `Bearer ${process.env.HOS_KEY}` } },
    )
    const body = await res.json()
    if (!body.success) throw new Error(body.error)

    runs.push(...body.runs)
    cursor = body.nextCursor
  } while (cursor)

  return runs
}
```

Three rules keep that loop correct:

1. **Stop on the list's own signal.** On a cursor list, a page can come back
   smaller than `limit` and still have more behind it.
2. **Send the cursor back unchanged.** It is an opaque string. Do not parse it,
   build one, or carry one between different queries.
3. **Do not skip a page.** Cursors are sequential. A cursor list has no offset
   to jump to.

## What a cursor guarantees

A cursor marks a position in the result, not an offset into it. Records created
while you are paging appear at the start of the list and do not shift the pages
below, so a page is not skipped or repeated because the data changed mid loop.
This matters most on lists that grow quickly, which is where offset based paging
returns duplicates.

What it does not do is freeze the data. A record changed after you read its page
is returned as it was when you read it. If you need a consistent view, compare
timestamps on the records rather than assuming the pages were a snapshot.

## Cursors belong to one query

A cursor encodes the ordering of the query that produced it. Change the filters,
the sort direction, or the operation, and the cursor no longer means anything.
Start that new query without one.

What happens to a cursor that is not valid depends on the list. Some return the
first page as if no cursor was sent, and some refuse it with `400`. The
operation's page says which. If a loop appears to repeat itself, check that you
are sending the newest cursor.
