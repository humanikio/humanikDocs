---
title: Let jobs use your browser
description: An opt-in surface that drives your real browser, why it is different from every other tool, and how to turn it on.
---

A flavor B device can drive your actual browser: open pages, click, type, read the
console, read network requests, fill forms. It uses **your** Chrome, with your
existing logins, so there is no OAuth to set up and no API connector to configure.

It is off by default and stays off until you turn it on. This page explains what
you are agreeing to, then how to do it.

The browser integration itself is part of Claude Code. Its extension, supported
browsers, and current limits are documented at
[Claude in Chrome](https://code.claude.com/docs/en/chrome). This page covers what
is specific to running it on a HumanikOS device: the two gates, what the daemon
can and cannot check, and what changes when a job is headless.

## Why this is not just another tool

Every other tool on a device acts **on that machine**, inside a workspace
directory the daemon derives and HumanikOS cannot name. That directory is the
blast radius. It is why a read-only ceiling is a real protection, and why widening
it to `Write` is a bounded decision.

The browser is not bounded by it.

It acts **as you**, in your real browser session, everywhere you happen to be
signed in: mail, banking, cloud consoles, your own admin panels. No value in your
config file makes that smaller. A remote job that can drive the browser inherits
every session the browser has.

It is not bounded by the **machine** either. Browsers pair to your Claude Code
account rather than to a host, so a browser signed in on a different computer, or a
different operating system, is reachable from a job running on this device.
Enabling this scopes the capability to every browser paired to that account.

That is the trade. It is a real capability with a real cost, and both halves are
worth stating plainly:

**What it buys you.** Reading a staging site's console errors and then fixing the
code that caused them. Filling a form to check validation actually fires.
Confirming a deploy rendered. Pulling structured data off a page. Working inside
an authenticated app that has no API worth using.

**What it costs.** The containment that makes the rest of the device model
trustworthy does not apply here.

## Turning it on

### In the Humanik OS app

1. Open **Frameworks**, then the **Claude Code** tab.
2. Find the **Browser (Claude in Chrome)** section and turn on **Let jobs use
   Chrome**.
3. Press **Save and restart** at the bottom of the page. humanikd restarts with
   the browser on.
4. Under **What Chrome needs**, each line shows a tick when that step is done. Do
   the ones that are not ticked (see [What you have to do by hand](#what-you-have-to-do-by-hand)).
5. Link this computer's Chrome (see [Link this computer's Chrome](#link-this-computers-chrome)
   below). Until you do, browser jobs on this computer are refused.

The switch writes the two lines below for you.

### In config.yaml

Two lines, and they do different jobs. **Both are required.**

```yaml
backend:
  claude_agent:
    allowed_tools: [Read, Grep, Glob, mcp__claude-in-chrome]
    chrome:
      enabled: true
```

| | Controls | Without it |
| --- | --- | --- |
| `chrome.enabled` | Whether the browser tools are **loaded** | No browser at all |
| `allowed_tools` | Whether they may be **called** | Tools visible, every call refused |

Having one without the other is the quiet failure: the agent can see the browser
tools, tries one, and is denied. `humanikd verify` tells you which half is
missing.

`humanikd setup` asks a single yes/no question and writes both lines for you.
Default is no.

### Note the hyphens

```yaml
mcp__claude-in-chrome      # correct
mcp__claude_in_chrome      # matches nothing, refuses everything
```

Connector display names get normalised. `claude.ai Gmail` becomes
`mcp__claude_ai_Gmail`, and every other MCP rule you write follows that pattern.
The browser server does not get normalised. A rule written the normalised way
reads as configured and denies every call.

## What you have to do by hand

The daemon detects and reports. It never installs an extension, writes a manifest,
or launches a browser. Four steps, in this order:

1. **Install the [Claude extension](https://chromewebstore.google.com/detail/claude/fcoeoabgfenejglbffodgkkbkcdhcgfn)**
   and sign in. Chrome, Edge, Brave or another Chromium browser. Not supported in
   WSL. `humanikd verify` prints this same link when the extension is missing.
2. **Run `claude --chrome` once**, in a terminal, as yourself. This writes the
   native-messaging handshake that lets the extension talk to Claude Code.
3. **Quit and reopen your browser.** It reads that handshake file *only at
   startup*. Skipping this is the most common failure by a wide margin. A correct
   setup that reports the extension as missing.
4. **Grant the sites you want reachable**, in the extension's own settings.

Then:

```bash
humanikd verify
```

It re-checks 1 through 3 and lists whatever is outstanding. It cannot see step 4,
site permissions live inside the extension and nothing outside it can read them.

Its browser-running check is **local only**. `verify` looks at this machine and
cannot see a browser paired on another one, so "no Chromium browser running on this
machine" means *not observed here*, not *nothing is reachable*.

## Which Chrome jobs use

Browsers belong to your Claude account, not to a computer. If the same Claude
account is signed in to Chrome on two computers, a job on either computer can see
both browsers. Chrome also remembers the browser that was picked last on the
account, and a browser action that does not pick a browser goes to that one, even
when it is on another computer.

So humanikd ties browser jobs to the Chrome on the computer the job runs on. We
call this linking the computer's Chrome.

### Link this computer's Chrome

In the Humanik OS app:

1. Open Chrome on this computer, in the profile you want jobs to use. Check that
   the Claude extension is signed in there.
2. Open **Frameworks**, then the **Claude Code** tab, and find **Browser (Claude
   in Chrome)**.
3. Press **Link this computer's Chrome**. It takes a few seconds. humanikd asks
   the Claude extension which browser is on this computer and saves it. Nobody is
   asked anything, on this computer or any other.
4. If more than one Chrome profile on this computer is signed in, the page lists
   them as Profile 1, Profile 2 and so on. Press **Use this profile** on the one
   jobs should use. Each row shows when that profile connected, because Chrome
   does not say the profile's name: the profile you opened last connected last.
5. When it is linked, the page says that jobs here use only this computer's
   Chrome, and the line **This computer's Chrome is linked** shows a tick.

In a terminal, the same steps are:

```bash
humanikd chrome link            # link, or list the profiles when there are several
humanikd chrome link --pick     # choose a profile by its number
humanikd chrome status          # show what is linked
humanikd chrome unlink          # remove the link (browser jobs are then refused)
```

You do not need to restart humanikd. Each job reads the link when it starts.

### What happens in a job

Chrome remembers the browser picked last on your Claude account, and a browser
action that does not choose a browser goes to that one, even when it is on
another computer. So humanikd adds a check (a Claude Code hook) to every browser
job. Claude Code runs it before each browser action, outside the agent, so the
agent cannot skip it.

| The job tries to | Not linked | Linked, before it selects | Linked, after it selects |
| --- | --- | --- | --- |
| Select this computer's linked Chrome | Refused | **Approved by humanikd** | **Approved by humanikd** |
| Select any other browser | Refused | Refused | Refused |
| List or switch browsers | Refused | Refused | Refused |
| Any other browser action (open a page, click, type, read) | Refused | Refused | Allowed, and Claude Code's own checks still apply |

- **Selecting the linked Chrome is approved by humanikd.** Claude Code's safety
  check can refuse a select that nobody in the chat asked for. You already chose
  this browser when you linked it, so humanikd tells Claude Code the select is
  approved. This is the only call humanikd approves. It does not approve what a
  job does on a web page.
- **A refused action does not end the job.** The agent is told why and which
  browser to select, and normally selects this computer's Chrome and goes on.
- **Each job selects again.** The selection belongs to one job, because another
  computer may have become the browser picked last in between.
- **Until this computer's Chrome is linked, every browser action is refused,**
  even when the account has only one browser, because that browser can be on
  another computer.

Each Chrome profile signed in to the Claude extension counts as its own browser.
Only profiles on this computer can be chosen, and jobs never use the others.

Link again after you reinstall the extension or change your Chrome profile.

Each link attempt, and why one failed, is recorded. Each browser job's choice,
and each refused action, is written to humanikd's log. You can read both in the
app under This machine, then Logs, with the Browser filter.

### When linking or a browser job fails

| What you see | What to do |
| --- | --- |
| `None of the browsers on your Claude account is on this computer` | Chrome is not open on this computer, or the Claude extension there is signed out or signed in to another Claude account. Open Chrome, check the extension, and link again |
| A list of Chrome profiles to choose from | More than one Chrome profile on this computer is signed in. Press **Use this profile** on the one jobs should use, or run `humanikd chrome link --pick` |
| `The list of Chrome profiles is out of date` | More than 10 minutes passed since the list was made. Press **Link this computer's Chrome** again |
| A job says `this computer's Chrome is not linked` | Link it, as above. No restart is needed |
| A job says `call select_browser with deviceId …` | The agent tried a browser action before selecting this computer's Chrome. It is told which browser to select and normally goes on by itself |
| A job keeps being refused after selecting | The linked Chrome may be closed, or its extension was reinstalled and has a new id. Open Chrome and link again |

## Requirements and traps

**You must be signed in with `claude` → `/login`,** on a Pro, Max, Team or
Enterprise plan.

**If `ANTHROPIC_API_KEY` is set, the browser silently does not work.** Claude Code
turns the integration off for API-key and long-lived-token credentials, because
the extension cannot authenticate with them, and it does so without an error.
Everything else about the device looks correct. `humanikd verify` flags this
specifically, because nothing else will.

Not available through Bedrock, Vertex or Foundry.

## Site permissions are the layer we cannot help with

There are two independent permission systems here.

**Yours, in the extension:** which sites Claude may browse, click and type on.

**The device's, in your config:** the `allowed_tools` ceiling, enforced by the
daemon.

A device runs headless under `permission_mode: dontAsk`, which means there is
nobody to answer a prompt mid-job. Site permission was never a Claude Code prompt
to begin with, since it belongs to the extension, so a job against a site you have not
granted has no approval path and will not proceed.

**Grant the sites you expect to use, ahead of time.** This is the one piece of
setup that has to be done before it is needed rather than when it is asked for.

Claude also stops and asks for a human whenever it reaches a login page or a
CAPTCHA. It does not attempt to authenticate as you. On a headless device that
means the turn ends rather than proceeding.

## One browser, many jobs

Concurrent jobs on a device share one browser and **are not isolated from each
other**. Listing tabs returns every tab, so one job can see, and act on,
another's work.

There is no cap on concurrency and no per-job browser profile. This is the shape of
the feature, not something to route around. If jobs on this device must not see
each other's browsing, dedicate a machine.

## Devices that serve other people

If you set `mcp.scope: isolated`, the setting for a machine serving a workspace
whose users are not you, **humanikd refuses to enable the browser**, at startup
and at dispatch.

The reason is worth knowing, because it is not obvious. Isolated hides the MCP
servers you configured on the machine, so those users cannot reach your Gmail. It
does **not** hide the browser: that server is built into Claude Code rather than
configured in a file, so the flag that hides the others never sees it. Left alone,
isolated would hide your connectors while handing over your live browser session,
exactly backwards.

So the two settings are mutually exclusive. Pick one deliberately.

## Recording

Sessions can be captured as a GIF. A recording contains everything visible on
screen, including account details on any page you were signed into. Review one
before sharing it outside your team.
