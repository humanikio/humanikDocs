title: Environment variables and secrets
description: What a web service receives in its environment, the difference between service and account-wide values, when a change applies, and how to manage values through the API.
---

A web service reads its configuration from environment variables. This page
covers where those variables come from, which ones your app actually receives,
and how to set and read them through the HumanikOS API.

## Variables and secrets are the same thing

There is one store. Every value you set, whether the console calls it an
environment variable or a secret, is encrypted at rest, each value with its own
key. Changing a value encrypts it again with a new key.

Values are kept in named groups. A group, such as `stripe`, holds fields, such as
`STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET`. **Each field becomes one
environment variable**, named after the field. The group name is only for you: it
never reaches the app.

| Term in the API | What it is |
| --- | --- |
| Secret (`secretName`) | A named group of fields |
| Field (`fieldName`) | One variable. Its name is the variable's name, its value is the variable's value |

If two groups on the same service hold a field with the same name, only one of
the two values arrives. Keep field names unique across a service's groups.

## Service values and account-wide values

| | Service | Account-wide |
| --- | --- | --- |
| Kept for | One service | Your whole Humanik Cloud account, not one project |
| Received by a web service | **Yes**, when a machine starts | **No**, unless you copy it to the service |
| In the API | Send `serviceId` | Leave `serviceId` out |

**A web service does not receive account-wide values.** To give one to a service,
copy it with
[Copy an account-wide secret to a service](/docs/api-reference/cloud/secrets/transferCloudSecret).
The copy is a snapshot: it is encrypted again under the service, and a later change
to the account-wide value does not reach it. Change the copy, or copy again under a
new name.

Account-wide values are also the tenant vault that office integrations point at.
See [Integrations](/docs/integrations#two-vaults-and-the-choice-matters).

### Groups for production and sandbox

Each service, and the account, has three groups of values:

| Console label | In the API | Read by a deployed machine |
| --- | --- | --- |
| Deployed (legacy) | Leave `environment` out | Yes |
| Production | `environment=prod` | Yes. On a name clash, this value wins |
| Sandbox | `environment=dev` | No |

That is the default. A service's `secretEnvironment` setting can narrow it:
`prod` reads only the Production group, `dev` reads only the Sandbox group. Any
other value is treated as unset. Set it with
[Update service settings](/docs/api-reference/cloud/services/updateCloudServiceUserConfig).

**The API treats each group separately.** A list or a read without `environment`
sees only the Deployed (legacy) group. To work with Production values, send
`environment=prod` on every call.

## What your app receives

The app's environment is built from nothing. It does not inherit anything from
the machine. It holds:

| Variable | Where it comes from |
| --- | --- |
| Your service's fields | The groups above |
| `PORT` | The platform. Set last, so a field named `PORT` cannot change it. Set only when the app runs, not during install or build |
| `NODE_ENV` | `production`, during install, build and run, unless you set a field named `NODE_ENV` |
| `PATH`, `HOME`, `TZ`, `LANG` | The platform, so commands run normally |
| `JOB_RUN_ID`, `JOB_CRON_ID` | The platform, only for a [scheduled command](/docs/cloud/scheduled-requests#two-kinds) while it runs |
| Your build settings | Your service's settings, as below |

**Your build settings arrive as variables too.** Each setting stored on the
service is passed to the app under its name in capitals with underscores:
`GIT_REPO_URL`, `GIT_BRANCH`, `BUILD_COMMAND`, `START_COMMAND`,
`INSTALL_COMMAND`, `ROOT_DIRECTORY`, `RUNTIME`, `IDLE_TIMEOUT_MINUTES`,
`SECRET_ENVIRONMENT`, and so on. Only settings you have stored appear. Size and
network settings are not passed. Do not give a field one of these names.

**Some names never arrive.** A field named `GITHUB_TOKEN` is dropped. The token
that clones your repository is never given to your app.

`NODE_ENV=production` makes `npm` skip `devDependencies` during install. If your
build needs a tool listed there, move it to `dependencies`, or set a field named
`NODE_ENV`.

### Values with line breaks

**A line break in a value arrives as the two characters `\n`**, not as a line
break. A private key in PEM format, for example, must be turned back into lines by
your app before it is used:

```js
const privateKey = process.env.PRIVATE_KEY.replace(/\\n/g, '\n');
```

### Names

A field name can be 1 to 256 characters. It cannot contain `/`, `?`, `#`, `%`,
`\` or a control character, and it cannot be `.` or `..`. Nothing else is
checked, so use capital letters, digits and underscores to get a name every
language can read from the environment.

## When a change applies

**Variables are read when a machine starts.** A running machine keeps the values
it started with, including after a value is changed or deleted. A change applies
to the next machine that starts: after a deploy, or the next time the service
wakes from sleep. To apply it now,
[redeploy](/docs/api-reference/cloud/deployments/redeployCloudService) the
service.

## Who can read a value back

Values can be read back after they are written, in plain text, by anyone with
the right permission. Plan your roles around that.

| To | Through `/cloud/secrets/protected` | Through `/tenant/secrets` (account-wide only) |
| --- | --- | --- |
| See which groups and field names exist | `cloud:read` @ `console` | `secrets:list` or `secrets:read` @ `console` |
| Read a value | `cloud:manage` @ `console` | `secrets:read` @ `console` |
| Create or change a value | `cloud:manage` @ `console` | `secrets:write` @ `console` |
| Delete a group | `cloud:manage` @ `console` | Use `/cloud/secrets/protected` |

`cloud:read` alone can never see a value. A role that should only look at
services can hold it safely.

The two paths reach the same account-wide values. A role holding `secrets:read`
at `console` can read every account-wide value without holding any `cloud:*`
permission. See [Roles](/docs/access-control/roles).

## Managing variables with the API

Every call goes to the HumanikOS API with a service account key, or a console
login, holding the permission in the table above. There is no separate Humanik
Cloud credential.

Get the service ID first, from
[List services](/docs/api-reference/cloud/services/listCloudServices):

#### Request

```bash
curl "$HOS_API/cloud/services" \
  -H "Authorization: Bearer $HOS_KEY"
```

### Set a variable on a service

Create the group, then add a field to it.

#### Request

```bash
curl -X POST "$HOS_API/cloud/secrets/protected" \
  -H "Authorization: Bearer $HOS_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "secretName": "stripe", "serviceId": "svc_7f3a9c2e" }'
```

#### Response `201 Created`

```json
{
  "success": true,
  "data": {
    "secretName": "stripe",
    "tenantId": "nt_5b21e9c4",
    "serviceId": "svc_7f3a9c2e",
    "created": true,
    "timestamp": "2026-10-19T14:02:11.482Z"
  },
  "status": 201
}
```

#### Request

```bash
curl -X POST "$HOS_API/cloud/secrets/protected/stripe/fields" \
  -H "Authorization: Bearer $HOS_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "fieldName": "STRIPE_SECRET_KEY", "fieldValue": "sk_live_51Hx4c2Ab9", "serviceId": "svc_7f3a9c2e" }'
```

#### Response `201 Created`

```json
{
  "success": true,
  "data": {
    "secretName": "stripe",
    "fieldName": "STRIPE_SECRET_KEY",
    "created": true,
    "dekVersion": 1,
    "timestamp": "2026-10-19T14:02:12.103Z"
  },
  "status": 201
}
```

To change it later, use
[Update a secret field](/docs/api-reference/cloud/secrets/updateCloudSecretField).
To work in the Production group instead, add `"environment": "prod"` to each body,
or `environment=prod` to each query.

### Apply it

#### Request

```bash
curl -X POST "$HOS_API/cloud/services/svc_7f3a9c2e/redeploy" \
  -H "Authorization: Bearer $HOS_KEY"
```

The service is down while a redeploy runs. See
[Deployments and logs](/docs/cloud/deployments-and-logs).

### Read a value back

This needs `cloud:manage`. The field name follows the group name directly, with no
`/fields/` in the path.

#### Request

```bash
curl "$HOS_API/cloud/secrets/protected/stripe/STRIPE_SECRET_KEY?serviceId=svc_7f3a9c2e" \
  -H "Authorization: Bearer $HOS_KEY"
```

#### Response `200 OK`

```json
{
  "success": true,
  "data": {
    "secretName": "stripe",
    "fieldName": "STRIPE_SECRET_KEY",
    "value": "sk_live_51Hx4c2Ab9",
    "dekVersion": 1,
    "timestamp": "2026-10-19T14:05:40.871Z"
  },
  "status": 200
}
```

### Copy an account-wide value to a service

List the account-wide groups by leaving `serviceId` out:

#### Request

```bash
curl "$HOS_API/cloud/secrets/protected" \
  -H "Authorization: Bearer $HOS_KEY"
```

Then copy one to the service:

#### Request

```bash
curl -X POST "$HOS_API/cloud/secrets/protected/transfer" \
  -H "Authorization: Bearer $HOS_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "secretName": "sendgrid", "targetServiceId": "svc_7f3a9c2e" }'
```

The copy goes into the service's Deployed (legacy) group. It fails with `409` if
the service already has a group with that name; send `targetSecretName` to give
the copy another name.

### Account-wide values through `/tenant/secrets`

The same account-wide values can be managed with `secrets:*` permissions instead
of `cloud:*`. This path reaches only the account-wide Deployed (legacy) group. Use
it when you manage values for office integrations: changing a value here also
marks every office whose integrations use it as needing a restart.

#### Request

```bash
curl -X PUT "$HOS_API/tenant/secrets/sendgrid/fields/SENDGRID_API_KEY" \
  -H "Authorization: Bearer $HOS_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "fieldValue": "SG.k7Qb2xT9" }'
```

See [Account secrets](/docs/api-reference/cloud/account-secrets/listAccountSecrets)
for every operation.

## There is no way to remove one field

Neither path deletes a single field. To remove a variable, delete its whole group
with [Delete a secret](/docs/api-reference/cloud/secrets/deleteCloudSecret) and
create the group again with the fields you want to keep.
